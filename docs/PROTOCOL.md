# Beldex Dapp Protocol — v1

**Status:** Draft-frozen for implementation · **protocolVersion:** `1` · **Date:** 2026-08-11

This document is the **single source of truth** for the wire protocol between:

- the **SDK** — the `bdx-web3js` npm package running in a web page, and
- the **Wallet** — the Beldex Wallet Extension's dapp bridge (inpage script, content script, background router, approval UI).

Both implementations MUST conform to this document. A change needed by either side MUST be made here first. The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as in RFC 2119.

---

## 1. Transport

All traffic travels over `window.postMessage` on the dapp page, relayed by the extension's content script. Three envelope kinds exist. Any message not exactly matching one of these shapes MUST be silently dropped by the receiver.

```ts
/** dapp → wallet */
interface RpcRequest {
  target: 'beldex-contentscript'
  id: string                     // UUID v4, generated by the SDK per request
  method: BdxMethod
  params?: object                // method-specific, see §4
}

/** wallet → dapp, terminal reply to one RpcRequest */
interface RpcResponse {
  target: 'beldex-inpage'
  id: string                     // echoes the request id
  result?: unknown               // present iff success
  error?: { code: number; message: string }  // present iff failure; never both
}

/** wallet → dapp, unsolicited push (connected origins only, except where noted) */
interface RpcEvent {
  target: 'beldex-inpage'
  event: BdxEvent
  data?: unknown                 // event-specific, see §5
}
```

Rules:

- Every `RpcRequest` MUST receive exactly one `RpcResponse` with the same `id`, unless the page unloads first.
- The SDK MUST ignore responses whose `id` matches no pending request.
- `id` values are generated in the page's main world; the Wallet MUST treat them as opaque strings and MUST NOT interpret or reuse them.
- All amounts anywhere in the protocol are **strings of atomic units** (1 BDX = 10⁹ atomic units; `u64` range exceeds IEEE-754 float precision). Numbers MUST NOT be used for amounts.
- Timeouts are an SDK concern, not a protocol concern; the Wallet MAY reply at any time, and replies to timed-out requests are ignored per the pending-id rule. SDK defaults: 30 s for auto-answered methods, 5 min for approval-gated methods.

### 1.1 Versioning

`protocolVersion` is an integer, currently `1`, reported in the `bdx_getNetwork` result.

- **Additive** changes (new methods, new optional params, new response fields, new events) do not bump the version. Receivers MUST ignore unknown fields and unknown events; the Wallet MUST answer unknown methods with error `-32601`.
- **Breaking** changes (removed/renamed fields, changed semantics) bump `protocolVersion`. A v(n) SDK talking to a v(n+1) Wallet MUST detect the mismatch via `bdx_getNetwork` and surface it; the Wallet SHOULD keep answering v(n) methods for one major version where feasible.

## 2. Discovery handshake

Namespaced adaptation of EIP-6963, using `window` `CustomEvent`s in the page's main world:

```ts
// dapp broadcasts (any time, typically at startup):
window.dispatchEvent(new CustomEvent('beldex:requestProvider'))

// wallet inpage script responds (and also announces once, unprompted, at injection):
window.dispatchEvent(new CustomEvent('beldex:announceProvider', {
  detail: Object.freeze({
    info: {
      uuid: string,     // random per page-load, NOT stable — for de-duplication only
      name: 'Beldex Wallet',
      icon: string,     // data: URI, SVG or PNG, ≤ 96×96
      rdns: 'io.beldex.wallet'
    },
    provider: BeldexProvider
  })
}))
```

- The Wallet MUST respond to every `beldex:requestProvider` (dapps may listen late).
- The Wallet MUST also assign the provider to `window.beldex` **iff** that property is undefined; it MUST NOT overwrite an existing value.
- Dapps SHOULD use the handshake (via the SDK's `detectProvider()`); `window.beldex` is a compatibility fallback.

### 2.1 Provider object

```ts
interface BeldexProvider {
  request(args: { method: BdxMethod; params?: object }): Promise<unknown>
  on(event: BdxEvent, listener: (data: unknown) => void): void
  off(event: BdxEvent, listener: (data: unknown) => void): void
  readonly isBeldex: true
}
```

The provider object MUST be frozen (`Object.freeze`) by the Wallet.

## 3. Access tiers

| Tier | Meaning |
|---|---|
| **public** | Answered without any grant. MUST NOT reveal addresses, balances, or wallet count. |
| **connected** | Requires a prior `bdx_connect` grant for the calling origin *and* the currently active wallet. Otherwise error `4100`. |
| **approval** | Every call requires fresh, explicit user approval in the Wallet's approval window. No auto-approval, no caching of consent. |

A grant is scoped to the pair *(origin, walletId)*. Switching the active wallet invalidates all grants of the previous wallet's pairs for event/read purposes (see `accountsChanged`, §5). Origins are as defined by the HTML origin concept; the Wallet MUST derive the origin from the browser-provided sender metadata, never from message payloads.

## 4. Methods

`type BdxMethod` is the union of the method names below.

### 4.1 `bdx_connect` — approval

Request the calling origin be granted access to the active wallet.

```ts
params: {}                       // MUST be empty or absent
result: {
  address: string                // active wallet's primary address
  network: 'mainnet' | 'testnet'
}
```

- If the origin already holds a grant for the active wallet, the Wallet MUST resolve immediately without UI (idempotent).
- If the wallet is locked, the approval window MUST require unlock before consent.
- Errors: `4001` (rejected), `4901` (no wallet exists), `4999` (expired).

### 4.2 `bdx_disconnect` — connected

Revoke the calling origin's grant.

```ts
params: {}
result: {}                       // also fires the 'disconnect' event to this origin
```

Calling without a grant is not an error; result is `{}`.

### 4.3 `bdx_getAddress` — connected

```ts
params: {}
result: { address: string }      // active wallet's primary address
```

### 4.4 `bdx_getBalance` — connected

```ts
params: {}
result: {
  total: string                  // atomic units
  unlocked: string               // atomic units, spendable now
  approximate: boolean           // true while client-side key-image spent-filtering
                                 // is incomplete in the Wallet
  height: number                 // scan height the figures are valid at
}
```

The Wallet answers from its own LWS sync cache and MUST refresh the cache first if it is older than 60 s. The Wallet MUST NOT expose the view key or raw output data.

### 4.5 `bdx_sendTransaction` — approval

```ts
params: {
  to: string                     // Beldex address (standard | integrated | subaddress).
                                 // BNS names are NOT accepted — resolve first via
                                 // bdx_resolveBns so the user approves a concrete address.
  amount: string                 // atomic units, integer string, > 0. Required unless sweep.
  priority?: 1 | 2 | 3 | 4 | 5   // default 1; 5 = flash (instant)
  paymentId?: string             // only for non-integrated addresses; hex, 16 or 64 chars.
                                 // A Wallet MAY reject this field with -32602 (the v1
                                 // reference wallet does) — prefer integrated addresses.
  sweep?: boolean                // default false; if true, `amount` MUST be absent
}
result: {
  txHash: string
  fee: string                    // atomic units actually paid
}
```

- The approval UI MUST display: the requesting origin, the **full untruncated** recipient address, the amount in BDX (all 9 decimals), the priority (flagged if flash), and a fee figure (labelled "estimated" if not exact) — all before consent.
- The transaction MUST be built, signed, and broadcast entirely within Wallet contexts; no intermediate artifacts (unsigned tx, ring members, keys) ever reach the page.
- The Wallet MUST enforce a single in-flight send per wallet (dapp and panel flows share the lock); a second concurrent request fails with `-32603`.
- Errors: `4001`, `4100`, `4900`, `4999`, `-32602` (any param invalid), `-32603` (build/broadcast failure; message MUST be sanitized).

### 4.6 `bdx_signMessage` — approval

> **Implemented in wallet v1.1.** Signature encoding (this pins the v1.x addendum
> anticipated by earlier drafts): the Monero-convention `wallet2::sign` scheme —
> `keccak256(message)` signed with the account **spend key**
> (`crypto::generate_signature` Schnorr construction), encoded as
> `"SigV1" + monero_base58(c ‖ r)`. Interoperable with `beldex-wallet-cli`'s
> `verify_value` and the explorer's ownership checks.

```ts
params: {
  message: string                // UTF-8 text; Wallet MUST refuse non-text payloads
}
result: {
  signature: string              // "SigV1" + monero base58 (see above)
  address: string                // signing wallet's primary address
}
```

- The approval UI MUST show the origin and the full message text (scrollable).
- The Wallet MUST reject messages containing control characters (`\x00–\x1f`,
  `\x7f`) with `-32602` — a message must not be able to disguise its content in
  the approval card.
- The reference wallet limits messages to **512 characters** (`-32602` beyond);
  clients SHOULD stay within this.
- Errors: `4001`, `4100`, `4900`, `4999`, `-32602`, `-32603` (signing failure;
  message sanitized).

### 4.7 `bdx_verifyMessage` — public

```ts
params: { message: string; address: string; signature: string }
result: { valid: boolean }
```

Pure verification; MUST NOT touch secrets and MUST NOT require a grant.
`address` may be a standard or integrated address — the Wallet extracts the
spend public key and runs `crypto::check_signature`. Malformed signatures or
addresses that don't decode yield `{ valid: false }` or `-32602`, never a leak
of why.

### 4.8 `bdx_resolveBns` — public

```ts
params: { name: string }         // e.g. "shop.bdx"
result: {
  name: string
  address: string
  verified: false                // resolution trusts the Wallet's configured HTTPS
                                 // resolver; not proven on-chain. Dapps MUST display
                                 // the resolved address to the user.
}
```

Errors: `-32602` (malformed name), `-32603` (resolver unreachable / not found).

### 4.9 `bdx_getNetwork` — public

```ts
params: {}
result: {
  nettype: 'mainnet' | 'testnet'
  height: number                 // best-known chain height (cache; 0 if unknown)
  protocolVersion: 1
  walletVersion: string          // extension version, e.g. "0.2.0"
}
```

### 4.10 `bdx_getState` — public

```ts
params: {}
result: { state: 'locked' | 'unlocked' | 'no-wallet' }
```

Coarse only. MUST NOT reveal wallet count, names, or addresses.

## 5. Events

`type BdxEvent` is the union below. Events are pushed only to origins holding a grant for the active wallet, except `unlock`/`lock` which MAY also be sent to previously-granted origins so they can re-prompt.

| Event | `data` | Fired when |
|---|---|---|
| `connect` | `{ address: string, network: string }` | This origin's grant becomes active (approval or wallet unlock restoring a session). |
| `disconnect` | `{}` | This origin's grant is revoked (user revocation, wallet wiped, or `bdx_disconnect`). |
| `accountsChanged` | `{ address: string \| null }` | Active wallet switched. `address` is `null` — the new wallet requires a fresh `bdx_connect`; previous grants MUST NOT carry over. |
| `networkChanged` | `{ nettype: string }` | Wallet's configured network changed. |
| `balanceChanged` | `{ total: string, unlocked: string, height: number }` | Wallet's background sync observes a balance delta for the active wallet. |
| `lock` | `{}` | Wallet locked (manual or auto-lock). Connected reads will fail `4900` until unlock. |
| `unlock` | `{}` | Wallet unlocked. |

The SDK MUST tolerate unknown events (ignore) and duplicate deliveries (events are at-least-once, not exactly-once, across service-worker restarts).

## 6. Errors

```ts
interface RpcError { code: number; message: string }
```

| Code | Name | Meaning / SDK guidance |
|---|---|---|
| `4001` | userRejected | User declined, or closed the approval window. Not an app error — show neutral UI. |
| `4100` | unauthorized | Origin holds no grant for the active wallet. Call `bdx_connect`. |
| `4900` | walletLocked | Wallet locked or unavailable. Prompt the user to open/unlock the wallet. |
| `4901` | noWallet | Extension installed but no wallet created. |
| `4999` | requestExpired | Approval not decided within the Wallet's TTL (5 min). Safe to retry. |
| `-32601` | methodNotFound | Unknown method (see §1.1). |
| `-32602` | invalidParams | Message MUST name the offending field; MUST NOT echo secret-adjacent data. |
| `-32603` | internal | LWS/WASM/other failure. Message MUST be sanitized — no stack traces, no internal state, no key material, no LWS URLs. |

Error `message` strings are for developers; dapps SHOULD map codes, not strings, to UX.

## 7. Security invariants (normative)

1. Keys, seed, and view key **never** cross the content-script boundary in either direction.
2. Every state-changing method requires a fresh, per-request approval showing the **origin prominently** (anti-phishing; punycode-decoded) and, for sends, the **full recipient address**.
3. Reads are gated on a prior `connect` grant; pre-connect, a page can learn only that a provider exists and the coarse `bdx_getState`.
4. Pending approvals expire after 5 minutes (`4999`); at most one pending approval per origin; read requests are rate-limited per origin; approval-window close = `4001`.
5. The content script relays only exact-shape envelopes (§1) and MUST verify `event.source === window`; the inpage provider object is frozen; request ids are UUIDs so a malicious page cannot spoof responses to other requests.
6. When the wallet is locked, approval flows require unlock first; the page learns nothing beyond error code `4900`.
7. Grants are per *(origin, wallet)*; wallet switches never silently transfer access (§5, `accountsChanged`).
8. The Wallet derives origins exclusively from browser sender metadata, never from payloads.

---

## 8. Conformance checklists

**SDK:** drops malformed envelopes; ignores unknown ids/events/fields; string-atomic amounts end-to-end (BigInt internally); never sends `target: 'beldex-inpage'`; SSR-safe.

**Wallet:** answers every request exactly once; silently drops malformed envelopes; unknown method → `-32601`; enforces §3 tiers and §7 invariants; freezes the provider; never overwrites an existing `window.beldex`.
